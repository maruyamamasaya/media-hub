# 構成とAWS従量課金の調査

確認: 2026-10-14 16:25頃（日本時間）。実AWS読取・現行作業ツリー・公式価格表を照合。AWSリソースや素材は変更していない。並行作業の未コミット変更を含む実装を調べたため、全コードが端末／Lambdaへ反映済みとは保証しない。

## 結論

このアプリのAWS構成は小さく、サービス数の削減を急ぐ必要はない。本人認証→閲覧用Lambda→非公開S3直接取得という構成を維持するのが妥当。現保存量の保存費だけなら月約39円相当。計画している原本20GB・月1〜5時間の利用でも、条件を守れば月2,000円目標には余裕がある。

問題は、画像ごとの管理情報再読込、大量画像に対する制限、暗号化フォルダの新規再送による複製、実転送量の把握不足。先に大容量の送信失敗と待ち時間を防ぎ、その後に通知・利用量の見える化を整える。旧試作コードの整理は保守面では有効だが、AWS料金を直接減らすものではない。

## 冗長性・拡大時の問題

### 1. 通常画像ごとにカタログ全体を取得・検証する

`backend/reader.py` の通常URL発行は、鍵設定GET→カタログ全体GET→全素材検証→ごみ箱のdeep copy→可視フォルダ判定→該当素材探索→署名。1画像のURLにS3管理情報GETが2回必要。S3から同リージョンLambdaへの読込はインターネット配信量とは別だが、GET料金・処理時間・メモリは増える。

ローカル模擬S3・平坦フォルダ・短いファイル名・3回平均の診断:

| 枚数 | カタログbytes | URL発行結果 | ローカル平均処理時間 |
| --- | ---: | --- | ---: |
| 100 | 55,748 | 200 | 1.12ms |
| 1,000 | 555,248 | 200 | 10.06ms |
| 6,000 | 3,330,248 | 200 | 58.26ms |
| 10,000 | 5,550,248 | 400（4MiB超） | 上限拒否のため比較対象外 |

S3通信なしのMac測定でありLambdaの性能予測ではない。1万枚を同じカタログにすると、1枚の取得でも全件分の負荷が繰り返される。1万枚×3回の未キャッシュ表示なら管理情報GETだけ6万回、料金自体は約$0.0222だが、巨大JSONの再処理と待ち時間が主問題。

**優先案:** 認可とロックrevisionの検証を保ち、許可済み素材について小さな単位でURLをまとめて発行する。必要ならETag等で未加工カタログを再利用する。利用者別の可視結果を無条件に共有キャッシュしてはならない。新DB・Redisの追加は現規模では不要。

### 2. 1万枚という件数制限と4MiB制限が一致しない

`FolderUploads.scan` は1回1万件まで許すが、送信完了直前のカタログ生成で4MiB超を拒否する。合成の1万件で実際に超過。実ファイル名・versionId・階層により到達枚数が変わり、6,000枚なら常に安全とも保証できない。暗号化も管理JSONに4MiB制限がある。

この失敗では素材オブジェクトが先にS3へ保存され、一覧確定だけ失敗し得る。孤立した保存物は一覧に出なくても課金対象。

**最優先案:** 送信開始前に管理情報の推定bytesを検査して分割を案内し、サーバー確定後のversionId等にも余裕を取る。その後、フォルダ単位／ページ単位のカタログ分割を検討。今回は実素材を大量送信して再現していない。

### 3. 初回サムネイル取得の待ち時間と再取得

`ios/PhotoHub/SealedViewer.swift` の共通ゲートは通常／暗号化URL発行を600ms間隔にする。単純に30枚で最後の発行開始まで約17.4秒、100枚で約59.4秒＋通信。LazyVGridが表示対象だけ取得するため、1万枚全件を起動時に必ず読むわけではないが、全件未キャッシュなら発行枠だけで約100分になる。

通常写真・小画像は現在512MiBの端末キャッシュを先に使う。従来の料金資料の「端末へ長期キャッシュしない」は通常iOS画像には既に当てはまらない。1万枚×50KBなら小画像だけで約500MBとなり、原本キャッシュとの競合で追い出される可能性がある。

暗号化小画像は表示終了でimageとreaderを破棄し、端末永続キャッシュなし。1小画像の初回取得はURL発行API＋S3 HEAD 2回＋Range GET 2回。戻る／スクロールで再作成されたビューは再取得し得る。鍵保護のための意図された違いだが、解除中だけの共有メモリキャッシュは改善候補。再ロック時の破棄は必須。

### 4. 履歴が増えると通常一覧の全走査が重くなる

`GET /library` は最新を選ぶ前に、過去の全通常カタログをGETして検証する。50root／10ページの制限はあるが、小さなインデックスだけで最新を取る設計ではない。大量履歴では15秒timeoutや一覧失敗につながる可能性。無効な過去カタログ1個でも全体が失敗し得る。

暗号化一覧は100カタログ制限。新規送信計画ごとに別カタログが増えるため、長期利用で件数制限にも達し得る。

**優先案:** root別の最新参照を小さなインデックスで管理し、更新競合とごみ箱の仕様を保つ。原本や旧履歴の自動削除で解決しない。

### 5. 再送の重複はS3バージョニングだけでは測れない

通常キーはrootに結び付く相対パスID＋SHA256。同じ登録root・同じパス・同じ内容ならHEAD照合で送信を省略する。別フォルダへの複製、改名・移動、登録先の変更などでは同じbytesでも新しいキーになる。全体ハッシュ重複排除ではない。

暗号化キーはkeyID＋**送信計画ID**＋objectID。同じ計画の再試行は再利用するが、同じフォルダを再スキャンして新規計画で送ると別暗号文として全量追加され得る。通常＋暗号化の両方へ送っても両方分が課金される。現暗号文に重複があるかは未判定。

20GBの再複製1回につき保存費は約77円/月追加（同じ為替・税仮定）。この新しいキーの複製は「非現行バージョン5.7KB」の指標では発見できない。

**優先案:** 新規送信前に、同じ内容の送信履歴があることと追加保存量を表示する。強制的な全体重複排除は暗号化ID・認可・共有参照削除に影響するため、別設計とする。

### 6. コードと資料の重なり

現行はMac SwiftUI＋Python送信処理、iPhone閲覧専用。Web／Electron／旧iOSローカル同期／旧AWS署名APIを保持しており、保守する経路は多い。ローカルPythonからbackendのセキュリティ／ごみ箱処理をimportし、現行readerも旧 `app.py` のclient・response等を利用するので、旧コードを一括削除すると現行機能も壊れ得る。

`ARCHITECTURE.md`、`OPERATIONS.md`、`AWS-SETUP.md` には旧「未デプロイ」の説明が残る。標準verifyのYAML確認もauth/serviceが中心で、現行reader.yamlは明記されていない。現行／旧保全の見出し整理と検証対象の更新が必要。今回、これらの既存編集は上書きしていない。

**推奨:** 先に現行の入口・共有依存・検証対象を明確化し、その後に不要なUI経路を段階的に切り離す。SwiftUIとPythonはOS画面と送信処理を担当しており、別言語という理由だけで作り直す価値は小さい。

## 費用の判断

公式東京価格表を再取得: S3 Standard $0.025/GiB月、PUT/COPY/POST/LIST $0.0047/千回、GET/HEAD $0.00037/千回、通常インターネット転送は共有無料枠超過後の初段$0.114/GB。S3価格表公開2026-10-12、転送表公開2026-09-16。既存計画の主要単価と一致。

| 条件 | 月額の計画目安 |
| --- | ---: |
| 現在約10.25GBの保存だけ | 約39円 |
| 原本20GB＋軽量版5GB、動画1〜5時間、小画像1万枚を月2〜3回 | 約180〜310円 |
| 原本100GB＋軽量版25GB、同じ視聴条件 | 約560〜700円 |
| 同125GB、原画質約12.5Mbpsを5時間 | 約1,120円 |

後3行は[費用計画](COST-PLAN-2026-10-14.md)の仮定で、実測額・現在の動画bitrateではない。無料枠なし、150円/USD・税10%、軽量版は原本の25%、転送に10%余裕、小画像最大50KB、その他の小規模利用を含む。暗号化GET追加や再取得で変動。軽量版を作らず原本再生する場合は軽量版の料金目安を適用しない。

100GBの転送が全額有料なら転送だけ約1,881円、保存等を加えると月2,000円を超え得る。無料100GB/月はAWSサービス・リージョン横断共有なので、当アプリ専用の枠として扱わない。動画・原画質の反復取得と重複保存が主な変動要因。API/S3小リクエストだけを数円削るより効果が大きい。

API 2回/秒は月額上限ではない。30日連続で使えば約518万回、東京HTTP APIの従来単価$1.29/百万回ではAPI呼出だけ約$6.69（同仮定で約1,100円）、Lambda・S3・転送は別。発行済みURLからのS3取得はAPIのスロットルを通らない。予算通知にも課金停止保証はない。

小画像・管理JSONはStandardを維持するのが妥当。IAは最低128KiB課金や取出料、長期アーカイブは復元操作等の負担が増える。現在は旧版約5.7KBと未完了0件なので、自動削除による節約はほぼない。multipart7日破棄は課金対策として有効だが、7日以降の再開は既存パートがなくなり再送になる。

3. 最新カタログのインデックス化と現行／旧資料の整理を進める。
4. 既存$10予算の通知先と受信を確認し、必要なら早めの閾値へ調整。アプリ別の保存量・転送量を把握する。新しいS3有料メトリクス等は費用と便益を比較してから採用する。
