# 通常アップロードと分けた暗号化アップロード

2026-10-14、本人指定で追加。通常のS3フォルダと暗号化フォルダは別の入口・履歴・S3プレフィックスを使用する。既存の通常素材を自動で暗号化・移動・削除しない。

## 初回の鍵と復旧ファイル

Macの「暗号化アップロード」→「鍵を作って復旧ファイルを保存」。本人が12文字以上の長いパスワードを2回入力し、復旧ファイル（.mediahubkey）を保存する。ファイル保存に成功してから鍵をMacのKeychainへ登録する。通常の6桁フォルダPINとは別のパスワード。鍵をコードへ固定埋め込みせず、S3や閲覧Lambdaへ送らない。

iPhoneは「暗号化」または「設定 → 暗号化の鍵」→「復旧ファイルを読み込む」から、ファイルと同じパスワードで鍵をKeychainへ取り込む。普段の閲覧時には復旧ファイルのパスワードを再入力しない。Keychainは端末ロック解除中のみ・ThisDeviceOnly・自動同期なし。同じライブラリで1つの鍵を使い、既存と異なる鍵での上書きを拒否する。

復旧ファイルはiCloud Drive等で運んでも中身は暗号化されているが、パスワードと別に保管する。復旧ファイル・パスワードを失っても、鍵の残るMacでは「復旧ファイルを保存」で再発行できる。すべての端末の鍵と復旧手段を失うと復号できない。復旧ファイルは写真のバックアップではなく鍵のバックアップ。QR方式は採用していない。

## 表示と再非表示

起動時は暗号化の入口と鍵設定を隠す。MacはS3フォルダの「隠したフォルダを開く」、iPhoneは設定の同名ボタンから6桁PINを入力して表示する。初回はPINと確認を入力してその端末へ設定する。PINの検証情報は端末Keychainに保存し、自動同期せず、復旧ファイルにも含めない。MacとiPhoneはそれぞれ設定する。復旧ファイルの長いパスワードとは別で、PINは復号鍵ではない。

MacのKeychain確認中は、システム認証画面への一時的なフォーカス移動でPIN画面を閉じない。確認終了後も別アプリにいる場合は再ロックし、単にアクティブになっただけでは入力画面を再生成しない。

5回誤入力すると30秒待機し、失敗回数・待機期限はKeychainで保持する。入力したPINと一致する既存のフォルダ別鍵は同じ操作で解除する。異なる既存フォルダ鍵は解除しない。入口PINの変更・忘失リセット画面は未実装。

「閉じて隠す」、Macの非アクティブ化、iPhoneの背景移行で入口・復号画面を破棄する。再表示にはPINの再入力が必要。鍵はKeychainに保持し、復旧ファイルの再読込は不要。

## 送信と閲覧

複数フォルダをまとめて確認・予約し、ドラッグでも追加できる。少数並列・段階別進捗・残り時間目安・大容量の途中再開を提供する。再開用の暗号文だけを保持し、鍵と平文を永続保存しない。[アップロード改善](UPLOAD-IMPROVEMENTS.md)。

Macの「暗号化アップロード」でフォルダを選ぶ→内容・保存先を確認→暗号化送信をチェックして開始。原本・小画像・名前／階層／管理情報を暗号化して非公開S3へ送信する。元フォルダを保持。送信履歴・入力参照はMacのprivate作業領域にあり、入力原本自体はこの機能でMac上の暗号化へ置き換えない。鍵はローカルのアプリ管理プロセス内と匿名stdinだけで扱い、送信計画・ログ・コマンド引数へ保存しない。

Macの閲覧は通常フォルダと同じ正方形タイル・10pt名前表示、黒背景ビューア、左右ボタン／矢印キー、Escで一覧へ戻る操作。鍵設定は折りたたみ、ファイル切替時は前の動画と復号読込を終了する。

暗号化フォルダはMacとiPhoneの「暗号化フォルダ／暗号化」から閲覧。本人ログイン・保存鍵の両方が必要。通常フォルダの6桁PINとは独立し、鍵のある端末で暗号化フォルダを復号する。アプリが背面へ移ると表示を破棄する。iPhone側はGET限定。復号したサムネイル・画像・動画断片はメモリのみで、長期ディスクキャッシュを作らない。

画像は100MiBまで。動画は1MiBの認証付き暗号化単位で必要範囲だけ取得・復号し、AVPlayerに渡す。1ファイル5GiB、1回20GiB、10,000素材／フォルダ、管理情報4MiBの既存上限。HDR等の非対応小画像はアイコン表示。停止は処理中の小さい素材または現在の送信断片の完了後、失敗は本人が手動再試行。送信前の確認待ちは予定だけ取り消せる。元ファイルの変更・照合失敗では送信を止める。

## 暗号方式とデータ境界

暗号化・認証はApple CryptoKitのAES-256-GCM、ファイルごとの鍵はHKDF-SHA256。新しい暗号化ごとにランダムな16-byte saltと8-byte nonce prefixを生成し、32-bitの断片番号をnonceへ付加する。ヘッダーと断片番号を追加認証データとして結び付ける。別ファイル・別順序・改ざん・切断・違う鍵を拒否する。ヘッダー60 bytes＋各断片の認証タグ16 bytes。原本の平文SHA-256は暗号化管理情報内に保存し、画像の全体復号後にも照合する。

復旧ファイルはPBKDF2-HMAC-SHA256（600,000回・salt16 bytes）からパスワード鍵を導出してAES-GCMで保護し、復旧ファイルのパスワードをKeychainへ保存しない。

S3は `media-hub/encrypted-objects/{keyID}/{uploadID}/{objectID}.bin` と `media-hub/encrypted-catalogs/{keyID}/{uploadID}.bin`。キーには名前や原本ハッシュを含めない。S3既存の非公開・TLS・SSE-S3も維持し、Content-Typeはapplication/octet-stream。AWS側には暗号化バイト列と識別子・サイズ・個数等は見えるが、復号鍵・名前・メディア内容は渡さない。

アプリの分割ファイル形式はv1。暗号プリミティブを独自実装せず標準CryptoKitを使うが、第三者のセキュリティ監査を受けたとの主張はしない。OSスワップ・異常終了直後の一時ファイル・開発用デバッグ権限まで残留ゼロを保証しない。暗号化作業は一時的な入力スナップショットと暗号文を保持し、終了時・次回起動時に既知の作業ディレクトリを整理する。大きなファイルでは約2倍の作業空き容量＋余裕が必要。

## 構成と検証

共通暗号・鍵保管・動画断片読込はSources/PhotoHubCore/SealedMedia.swiftとSealedStreaming.swift。MacのMediaHubCryptoを同梱し、PythonのEncryptedUploadsは暗号化専用の独立した履歴と転送を管理する。閲覧APIの追加GET経路は本人JWT・ownerに限定し、暗号化領域だけの読取権限を追加する。既存の通常フォルダと本人ログインは維持する。

合成画像と0.3秒動画で実S3への暗号化送信、元ファイル保持、ciphertextのみの保存、実署名URLによるRange取得と復号・AVPlayerの動画読込を確認。検証の5版だけを削除し、本人素材・本番鍵は検証に使用しない。詳細は[検証方法](../TESTING.md)、[費用](COST-PLAN-2026-10-14.md)、[判断](../decisions/0017-separate-client-encrypted-uploads.md)。

## 費用

新たなKMS・常設サーバー・クラウド変換は追加しない。通常と暗号化の両方に同じ素材を送ると、その保存量は両方とも課金対象。暗号化自体の容量増は断片ごと16 bytesとファイルごと60 bytes。小画像では1回の取得にヘッダーと暗号化断片の2つのGETが必要で、転送・再試行・動画のシークは実量に従う。[費用更新](COST-PLAN-2026-10-14.md)。
