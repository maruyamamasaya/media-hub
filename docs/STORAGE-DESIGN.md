# ローカル主体の原本保管と端末間共有

Date: 2026-10-07
Status: 運用方針は合意済み。以下のデータモデル・処理・APIは次期設計で未実装。

## 目的と現在との差分
標準はローカル保管。共有が必要な原本だけリモート（初期候補は非公開S3）へ移し、確認済みの原本をローカルから外して端末容量を削減する。全素材の自動アップロードや二重保管を既定にしない。

現行は入力ファイルを専用objectsへコピーし、SQLiteのAsset/Fileと通常／アーカイブを管理する。任意ディレクトリの参照登録、Finder変更追跡、所在管理、リモート移動、共有メタデータ、原本キャッシュは未実装。今回の設計更新で既存ファイル・DB・API契約を変更しない。

## 独立して管理する状態
| 軸 | 値と意味 |
| --- | --- |
| 整理 | 通常／アーカイブ。タグ・所属を保持する一覧分類 |
| 原本の所在 | ローカル、リモート、両方。検証済みの所在から算出 |
| この端末の保持設定 | ローカル保管、リモート主体、この端末にも保持 |
| 利用可能性 | 利用可能、保管場所未接続、原本欠損、確認が必要 |
| 作業状態 | 転送待ち、送信中、照合中、共有登録中、ローカル整理待ち、完了、失敗、中断 |

整理状態から転送や削除を暗黙に実行しない。アーカイブはリモート専用とし、ローカルに戻した素材は通常扱いにする。リモート原本には通常利用用Standard、長期保管用Glacier Instant Retrievalを候補とするが、保存クラス変更は明示した保管ポリシーと独立ジョブで行う。「通常に戻す」だけで原本のダウンロード・保存クラス変更を自動実行しない。

「両方」はリモート移動中の一時状態でも生じる。両方に存在することと、利用者が端末への保持を指定したことを区別する。閲覧の一時キャッシュを永続的な二重保管と表示しない。

## 操作と表示
| 操作 | 結果 |
| --- | --- |
| フォルダを登録 | 既存ディレクトリを参照し、原本を複製せずカタログ化 |
| コピーして取り込む | 指定管理ディレクトリへコピー。入力元は保持する旨を表示 |
| リモートへ移す | 対象原本を送信・照合・共有登録し、成功した原本のローカル所在を外す |
| この端末にも保持 | リモート原本を指定ローカル保管場所へ取得・照合し、自動解放の対象外にする |
| 端末への保持を解除 | リモート原本の確認後、端末側の保持コピーを解放する。リモート原本は残す |
| 原本を開く | ローカルがあればそこから取得、リモートだけなら一時キャッシュ経由で取得 |
| アーカイブ／通常に戻す | 整理状態だけを変更 |

一覧・詳細に「この端末」「クラウド」「この端末にも保持」「別端末のみ」「未接続」等を表示し、配置と利用可能性を区別する。別端末の絶対パスを閲覧端末の有効パスとして扱わない。

一括操作は対象件数、原本合計容量、ローカルで解放予定の容量、入力元を削除するかを事前に表示する。完了件数・失敗件数・整理待ちを分け、原本送信だけを「移動完了」と表示しない。容量削減は実際の解放結果を集計し、ごみ箱や退避領域に残した分を差し引く。

## Finder・Explorerとディレクトリ
利用者が登録したディレクトリを保管場所にする。通常のファイル名と拡張子を保ち、Finder/Explorerから開く・移動・名前変更ができる。物理フォルダとアプリのコレクションは別物で、多対多の所属を維持する。

例：`素材ライブラリ/テクスチャ/木目.png`。ローカル物理パスはrootIdとrelativePathで表し、rootIdからこの端末の登録先へ解決する。端末が変わったら保管場所を再登録・照合する。素材IDは名前・パスから生成しない。ユーザー入力の任意パスをrendererから直接読み書きさせない。

保管場所はアプリ管理用と外部参照用を区別する。アプリ管理用は「リモートへ移す」の対象説明に従ってローカル原本を整理できる。外部参照用は削除対象となる実ファイルとフォルダを明示し、元ファイルの削除を利用者が選んだ場合だけ整理する。既存のコピー取り込みの入力元は別ファイルであり、移動操作で探索して消さない。

既存フォルダへの参照登録を標準経路とし、コピー取り込みも明示的な選択として残す。参照フォルダへDBや隠し管理ファイルを勝手に作らない。DB・設定・派生・一時キャッシュは端末内のアプリデータへ分離する。フォルダ全体に対する再帰削除は行わない。

## 次期データモデル
| Entity | 主な項目・責務 |
| --- | --- |
| Asset | 固定ID、libraryId、名前、タグ・所属、archivedAt、trashedAt、revision、共有範囲 |
| FileRevision | 固定ID、assetId、role、元ファイル名、MIME、byteSize、sha256、寸法。特定のバイト列を識別 |
| Device | 固定IDと表示名。端末固有の状態を識別 |
| StorageRoot | 固定ID、deviceId、表示名、管理／参照の区分、接続状態。絶対パスは端末ローカル情報 |
| FileLocation | fileRevisionId、local/remote、端末・rootId・relativePath又はリモートキー/版識別、検証状態・確認日時 |
| DeviceRetention | deviceId、assetId、保持設定、ローカル保管先。共有整理状態と分離 |
| StorageTask / TaskItem | 安定した作業ID、操作、対象版・revision、状態、照合結果、整理対象、失敗、再開地点 |
| CacheEntry | fileRevisionId、派生／原本一時キャッシュ、サイズ、最終使用、取得検証状態 |

一つの素材・原本版に複数の所在を持たせ、アップロード時に別Assetを作らない。パスの同一性と内容ハッシュを分ける。同じ内容を検出しても別ファイルを自動削除しない。既存の原本ハッシュ一意制約とAssetFile.objectKeyはこのモデルへ段階移行し、同じ内容の複数所在を別素材の重複登録と混同しない。

原本を外部編集した場合は新しいFileRevisionとして扱い、既存のリモート版を上書きせず、現行版の切り替えと再送信を別に記録する。タグ・メモなどは素材IDへ紐付けたまま保持する。

ローカル所在や保持設定は端末DBを正本とする。共有素材のタグ・コレクション・原本版・リモート所在は共有メタデータ側を正本とし、SQLiteへ同期して検索・閲覧する。ローカル専用素材は共有登録を要求しない。SQLiteファイル自体をS3へ置いて複数端末から直接編集しない。

## リモートへ移す処理と不変条件
1. 対象の素材revision、原本版、パス・ファイル同一性、ハッシュ、削除の対象と許可を永続ジョブへ固定する。
2. 送信するバイト列を固定する。既存原本を不用意に二重コピーせず、外部編集を排除できない場合だけ容量確認の上で一時スナップショットを用意する。元ファイルの版と送信版を記録する。
3. 安定した原本版IDのリモートキーへ送信する。マルチパート等を使う場合も、途中状態・再開情報を保存する。
4. リモート原本の存在・サイズ・SHA-256照合を確認する。ETagを一律に原本SHA-256として扱わない。照合方式はアップロード形式ごとに実AWSで検証する。
5. 共有メタデータへ原本版・リモート所在・必要な派生を登録し、同じ所有者の別端末から取得可能な状態を確定する。端末DBにも検証済みの所在を記録する。
6. 整理直前にリモート版の有効性、ローカル原本が送信した版と同じこと、素材の競合・ごみ箱移動がないことを再確認する。確認できなければローカルを残して「確認が必要」にする。
7. 許可された対象原本だけをローカルから削除し、所在・実解放容量を確定する。サムネイル・軽量派生・素材メタデータは残す。入力元や他のコピーは対象外。

リモート照合と共有登録が終わる前にローカル原本を削除しない。共有カタログとS3の書き込みは原子的でないため、ジョブと照合で回復する。アプリ経由のリモート削除は進行中の移動と競合させず、独立したライフサイクル規則で利用中原本を消す構成にしない。

Finderの書き換えと削除直前の確認の間にも競合が起き得る。対象の同一性・変更をOS操作で保護できない外部ファイルは自動削除せず、整理を保留する。ハッシュ一致だけで任意パスを削除する実装は採用しない。

元フォルダからファイルを外す操作はごみ箱への素材移動とは別。アプリ管理原本の削除は明示した「リモートへ移す」操作に含める。外部参照原本は削除範囲を別途確認する。OSごみ箱に移す実装の場合、実際に容量が解放されるまで削減成功として集計しない。

## 中断・失敗・再開
| 中断点 | 回復時の扱い |
| --- | --- |
| 送信前／送信途中 | ローカル保持、未完了転送を照合して再試行 |
| リモート照合前 | ローカル保持、リモート原本を検証するまで整理禁止 |
| 共有登録前 | 原本は残す。同じ作業IDで共有登録を再試行 |
| 共有登録後・ローカル整理前 | 一時的な両方保管。原本の再アップロードなしで整理を再開 |
| ローカル整理失敗 | クラウド保存済み・整理待ちを表示。削除対象を再確認して再試行 |
| ローカル削除後・DB確定前 | 検証済みリモート版とローカル実在を照合して所在を修復 |
| 原本の外部編集／所属・版の競合 | 変更された原本を残し、自動再送・自動削除を止める |

操作を逆転・取消する場合は既に完了した工程を確認する。ローカル整理後の取消はリモート原本を取得・照合する別作業として扱う。単なるボタン取消で元のローカル原本が戻ったと表示しない。

## 原本取得と端末容量
リモート原本の閲覧用取得は、容量上限を持つ一時キャッシュへ保存する。fileRevisionIdで識別し、取得途中は完成原本と区別する。空き容量を確認し、取得後に照合する。

古い未使用の一時キャッシュを解放する。閲覧中・取得中の原本、この端末にも保持した原本、唯一のローカル原本は自動解放しない。サムネイルと軽量派生にも別の容量上限を設け、再取得・再生成可能性を確認して整理する。

利用者が指定した場所へのエクスポートはキャッシュではなく、アプリの自動整理対象外。「この端末にも保持」は安定したローカル所在を新規登録し、ダウンロード成功前に保持完了を表示しない。

容量表示はローカル原本、保持コピー、原本キャッシュ、派生、staging/退避、DBを分ける。クラウド保管量とアップロード予定量は別表示。リモート利用は保存・取得・転送・リクエスト等の費用があり、頻繁に取得する原本には端末保持を使う。料金は導入時に[公式料金](https://aws.amazon.com/s3/pricing/)で再確認する。

## 端末間共有とDBの復旧
リモート保管した素材は、原本と共有カタログ・一覧用派生を他の認可された端末へ提供する。各端末の保持設定やローカルパスは共有整理情報に上書きされない。複数端末のタグ・所属編集は共有revisionで競合を検出し、削除はtombstoneで伝播させる。

共有メタデータの永続先は未選定。S3の原本キー一覧だけからタグや所属を復元できると扱わない。初期の原本連携と共有カタログは別の完了条件とし、共有登録の確定をローカル整理の必須条件にする。共有編集のオフラインキュー・自動マージは初期範囲外。

ローカルDBのバックアップに保管場所対応、所在、保持設定、ジョブ状態を含める。可搬メタデータ書き出しと読み戻しを提供する案。ローカル原本は登録した外部ディレクトリも別途退避が必要で、アプリデータだけのバックアップでは復元できない。共有原本はリモート版の存在と権限を確認して再接続する。

リモートへ移すことは原本の移動であり、それだけで独立したバックアップにはならない。リモートの誤削除・版保持・バックアップの方針は別に定め、その追加容量・費用も計上する。保持世代や期限は未確定。

## 再スキャンとファイル変更
まず明示的な再スキャン、起動時の必要な照合、利用直前の確認を提供する。常時監視は後で追加しても、監視イベントだけを唯一の正本にしない。大量素材は変更候補だけハッシュ確認し、必要時に全体照合する。

名前変更・移動はOSの同一性情報とサイズ・ハッシュ等を用いて再接続候補を作る。判別が曖昧なら利用者が候補を選ぶ。フォルダ外への移動は勝手に追跡・登録せず再リンク操作で許可範囲を更新する。外付けSSD未接続やFinder削除はDB・共有原本を自動削除する理由にしない。

同じパスに別内容が現れたら新しい原本版として検出し、旧リモート版を残す。シンボリックリンク、循環、登録root外へのアクセス、同じディレクトリの重複登録を検証する。

## 実装段階と受け入れ条件
| 段階 | 内容 | 完了条件 |
| --- | --- | --- |
| S1 | ローカル保管場所・参照登録・所在モデル | 原本の二重コピーなし、Finder/Explorerで扱える、既存ライブラリ保持 |
| S2 | 再スキャン・再リンク・外部編集検出・メタデータ退避 | 名前変更・移動・未接続・DB復旧でタグと原本の同一性を保持 |
| S3 | 転送ジョブ・容量表示・保持設定のローカル検証 | 隔離保存先で中断・競合・整理失敗を再現し、唯一の原本を失わない |
| S4 | 実S3原本・共有カタログ・本人認証 | 実AWS照合、別端末取得、共有登録前のローカル削除禁止を検証 |
| S5 | 明示的リモート移動・端末保持・原本キャッシュ | 端末容量削減、上限解放、再開・再取得・端末別設定を一巡 |

既存Web/iOSのデータは停止中に退避し、素材IDとFile IDを保持する移行を試験する。既存objectsのキーを所在として登録してから、利用者が選んだ読みやすいディレクトリへ明示的に移行する。起動だけで既存原本を移動・削除しない。新しい契約はJSON Schema、生成Web/Swift DTO、テスト例を同時変更する。既存APIの制限を変更する場合は別途検証する。

全段階でチェックサム不一致、送信中編集、削除直前編集、共有競合、ディスク不足、権限失敗、同名ファイル、再起動、二重処理、リモート欠損、別端末、アーカイブと所在の組み合わせを検証する。リモートのバックアップ/版保持と共有メタデータ方式、OSごとの外部ファイル整理手段、容量上限の既定値は導入前に確定する。

## 今回の確認用実装（2026-10-07）

Web／Windows試作で所在表示・所在フィルター・固定ローカルフォルダ読み込みを追加。DB v3以前の既存素材をdevelopment-remoteとして分類し、原本のパス・内容は保持する。新規取り込みはlocal。これは画面確認用で、実体は両方とも同じPC内にある。

- 原本はobjects/local-originalsの通常ファイル。ファイル選択は管理コピー、フォルダ読み込みは参照登録（永続的な原本コピーなし）。プレビューと素材情報は別途保存。
- アーカイブ操作・一覧はリモート専用。ローカル素材は通常のみ。
- 参照原本の移動はmissing、サイズ／更新日時変更はchanged。原本取得・再生成を止め、以前のプレビューを保持。自動追跡・同じパスの改訂登録は未実装。変更を戻すか別名で追加する。
- 参照素材の完全削除はDB・プレビューのみ。参照元を削除しない。管理コピーの従来の完全削除は維持。
- 手動読み込みは1回につき新規100件まで。重複ハッシュは既存素材として扱い、複数所在の統合はまだ行わない。
- 現段階では原本の所在は1つ。設計上のFileLocation複数所在、リモート移動・端末保持・容量解放、登録ルートの選択、共有カタログ／AWS接続は後工程。

この試作のdevelopment-remoteをS3へ移行済みとして扱わない。アプリ設定・詳細でPC内の模擬保存と明示する。確認用素材追加は停止中にscripts/create-local-storage-demo.pyを明示実行する。既存DBは追加前にSQLite backup APIで退避する。

## フォルダ同期と手動転送の実装（2026-10-07）

設定で毎回フォルダを選択／絶対パスを指定して手動同期できる。登録先をUUIDで記録し、移動後はその登録先を選んで新しいパスへ結び直す。同期は参照登録で、原本を複製しない。新規候補は1回100件まで、既登録の一致ファイルは上限を消費しない。

Asset IDは固定UUID、StorageRoot IDも固定UUID。relativePathは所在、原本SHA-256は完全一致するファイル内容の識別子。同一バイト列は既存Assetへ結び付け、同じ内容の改名／移動ならAsset ID・タグ・メモを維持する。再圧縮などバイト列の違う画像を見た目だけで同一判定しない。既登録パスの内容変更は変更として報告し、自動で以前の素材情報を上書きしない。

storage_rootsは端末固有パス、local_sourcesはrootId／relativePathと素材・ハッシュの対応。files.objectKeyのreferences/rootId/relativePathをローカルAPI内で解決する。フォルダ欠損は設定で表示し、同期時はfolder_missing。ファイル欠損・変更も通知し、素材を自動削除しない。見つからないフォルダの再指定で同じRoot IDを維持できる。複数の一致するローカルコピーは対応を記録するが、原本の優先所在は1つ。

素材詳細の歯車に「ローカルにダウンロード」「リモートにアップロード」を配置。ダウンロードは開発用リモートを保持し、ローカルの管理コピーを作る。アップロードは確認画面で参照元も削除対象と明示し、SHA-256照合→リモート対応・原本所在のDBコミット→ローカル原本削除。タグ・メモは維持する。ローカルへの転送時はアーカイブ分類を解除する。転送先を再利用し、異なる内容の転送先は上書きしない。

remote_originalsは保持する開発用リモートの対応、transfer_cleanupはコミット後の未完了整理。整理失敗や転送中の原本変更は削除せず、明示的な再試行を求める。再起動だけで参照元を削除しない。参照原本の通常の完全削除は元画像を残すが、転送確認に同意した移動では元画像も整理する。

全てPC内の模擬転送で、PC全体の容量削減にはならない。AWS・共有カタログは未接続。OS監視による自動同期、変更画像の改訂履歴、別端末のRoot再接続、見た目の類似検索は後工程。
